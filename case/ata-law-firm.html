Building privileged-access case management for a law firm

A single-tenant case management platform for a law firm, in daily production use by attorneys, staff, and clients. The build forced a real design decision on every page: how do you model attorney-client privilege in a relational schema and a permission system without leaking a single row across cases?

Role
Sole engineer, architecture, build, deployment
Stack
Laravel, Vue.js (Inertia.js), MySQL, Tailwind CSS, AWS (EC2, RDS, S3)
Status
In daily production use, with ongoing maintenance

Published 2026-05-16 · Updated 2026-10-27

The starting line

When the firm called me in, the entire practice ran on three things: shared spreadsheets in a cloud drive, a forest of Word templates named final_v3_REAL.docx, and email threads carrying attachments back and forth with clients. Cases lived in heads and inboxes. Deadlines lived in someone's calendar, maybe.

The brief was small in words and large in scope: get the firm onto a real system. Track cases. Generate documents without retyping client details. Let clients see their own case status without a phone call. Run it on AWS for trust reasons. Don't break anything during the rollout.

Constraints that shaped every decision

The non-negotiables drove the design more than the feature list did.

  • Attorney-client privilege. Two cases in the same firm, on opposing sides of a regulatory matter, cannot bleed data into one another. Not in search results, not in document references, not in recently-viewed lists, not anywhere.
  • Single tenant by default. The firm wanted their data on their own infrastructure, not shared with anyone else's. That ruled out off-the-shelf multi-tenant SaaS and set the AWS layout.
  • Solo build. No team, no on-call rotation. Anything I shipped had to be operable by one person, and recoverable by them.
  • Daily use from day one of rollout. No staging-only periods. The firm needed to keep practicing law while we migrated.

A deliberately boring architecture

One Laravel monolith serving Vue pages through Inertia.js, with a queue worker for document generation. A managed MySQL database that is not reachable from the public internet. Object storage for documents, encrypted at rest. A transactional email service. All of it on AWS, all of it single-tenant.

No microservices, no Kubernetes, no Redis cluster. A monolith was the right answer for a sole engineer running a firm-sized workload.

The document automation engine

Half the pain at the firm was retyping the same client name, case number, court details, and dates into ten different documents. Document automation is what gets a legal platform off the ground.

The core idea is simple: documents are templates with named placeholders, rendered against a case context. The surface area is small, but the failure modes are nasty in legal work, a wrong court address on a pleading is not just embarrassing.

Templates as data, not as files

Templates are stored as versioned records. When an attorney edits a template, the old version is not overwritten, a new version is added. Every generated document records the exact template version it was rendered from. If we ever need to ask "what did we send last June?", the answer is reproducible. 

// Illustrative sketch, names simplified
function renderTemplate(string $body, array $context): string
{
    return preg_replace_callback(
        '/\{\{\s*([a-z0-9_.]+)\s*\}\}/i',
        fn ($m) => Arr::get($context, $m[1], '«missing:'.$m[1].'»'),
        $body
    );
}

The «missing» sentinel is intentional. A silently-blank field on a legal document is worse than an obviously-broken one. Reviewers catch the angle brackets immediately.

Generation pipeline

When a document is requested, the request is queued, rendered to DOCX, then archived to object storage. The case references the generated artifact rather than embedding it. Documents become first-class entities with their own access rules, audit trail, and download history.

Access control under attorney-client privilege

The interesting problem on this build wasn't the documents, it was the access model. The naïve approach is to stamp an owner on every row and call it a day. That model is wrong for a law firm.

A case has multiple people legitimately attached to it: a lead attorney, an associate, a paralegal, the client. Each role sees a different surface. The client must never see internal billing notes. The associate must never see cases they were not assigned to. Searches and "recently viewed" lists must respect the case membership boundary, not just per-record permissions.

Membership over ownership

I built it around case membership: people are attached to a case with a role, and every read query that touches case-scoped data is constrained by that membership. The authorization policy layer enforces the same rule again at the record level. The two enforcement points back each other up, if one is bypassed, the other still holds the line. 

// Illustrative sketch, identifiers renamed
// 1. Query level: only rows from matters the user belongs to.
public function scopeAccessibleBy(Builder $query, User $user): Builder
{
    return $query->whereHas('matter.participants', fn ($p) => $p->whereKey($user->getKey()));
}

// 2. Record level: the same rule, checked again.
public function view(User $user, Document $document): bool
{
    return $document->matter->participants->contains($user);
}

Every search, list, and report path applies the membership scope explicitly. There is no global scope on the model, global scopes are easy to forget when writing a raw query during a hot fix. An explicit scope on every read is ugly and safe. I chose ugly and safe.

Lesson Defense in depth on authorization is not paranoia in legal software. It is the floor. The cost of a single cross-case leak is larger than the cost of writing the scope twice.

Client portal as a different surface

The client portal isn't a smaller version of the attorney UI, it is a different surface that happens to read from the same database. Clients sign in through a separate authentication path, and their access is deny-by-default: a record is visible to a client only if it has been explicitly marked as client-visible.

Whitelisting visibility, not blacklisting it, was the design principle I trusted most. Forgetting to hide something is a much easier bug to write than forgetting to expose something.

AWS infrastructure decisions

Why a monolith on a single server

Tempting alternative architectures for a 2026 portfolio piece: ECS Fargate, Lambda for document generation, ElastiCache, a queue on SQS, observability on CloudWatch Logs Insights. All defensible. None of them were the right call here.

The firm's workload is a small number of concurrent users and a modest volume of background document generation. A single appropriately-sized server handles it with headroom. ECS would have added control-plane operations I did not want to run alone. Lambda would have added cold-start variance on document generation that the firm would feel. The monolith is boring; the monolith ships.

What I did invest in

  • Automated database backups with point-in-time recovery. The cost is small. The peace of mind is large.
  • Versioned document storage. A deleted or overwritten document is recoverable.
  • Secrets off the disk. Nothing sensitive lives in a config file on the server or in the repository. Secrets come from a managed secret store at deploy time.
  • Download links scoped to one case. Signed download links are issued only after the membership check and only cover that case's documents. A leaked link still cannot reach another case.

What broke, or surprised me

Templates are software, not content

I shipped the first version of templates editable as freeform rich text. Attorneys promptly typed their own hand-made name and date markers into the text, alongside the real placeholder tokens. Renders looked correct until they didn't. The fix was a template-authoring UI that inserts placeholders as visual chips, not as raw text. Templates had become software, they needed an authoring environment, not a text box.

Mobile portal usage was far higher than I assumed

The client-side traffic skewed heavily toward phones. The original portal was responsive but designed for the desktop case detail first. Early after launch I rebuilt the mobile portal around a short single-column flow with case status, latest documents, and a message-attorney button, three taps from the home screen to anything that mattered.

Document download spikes

Periodic bulk exports pulled a burst of large documents at once. The first version streamed them through the Laravel app. After watching the app server sweat, I moved downloads to short-lived signed storage URLs, issued only after the requesting user's case membership is checked. The app issues the URL, object storage serves the bytes. The app's job is authorization, not file delivery.

Design decisions

The interface choices on this build came straight out of the constraints and the surprises above.

  • The portal is its own surface

    Clients get a separate sign-in and a separate UI, not a trimmed attorney screen. Nothing is visible to them unless a record is explicitly marked client-visible.

  • Phone first for clients

    Once usage showed clients mostly on phones, the portal became one short column: case status, latest documents, and a message-attorney button, three taps from home.

  • Placeholders as chips

    Attorneys typed their own hand-made name markers into the rich text. The template editor now inserts placeholders as visual chips, so a template cannot hold a token the engine does not know.

  • Loud failures on documents

    A missing field renders as «missing» instead of a blank. A broken-looking document gets caught in review; a quietly empty one gets filed.

What it does today

  • Active daily use across the firm, attorneys, paralegals, and the firm's clients.
  • Case tracking with status, deadlines, and a per-case timeline.
  • Document automation generating standard pleadings, contracts, and client correspondence from versioned templates.
  • Client portal with case status, document downloads, and direct messaging to the assigned attorney.
  • Audit trail of who viewed, edited, or downloaded what, visible to firm administrators.

The spreadsheet workflow is retired. The firm has not asked to go back.

What I'd do differently next time

  • Filament admin from day one. I built the internal admin screens by hand. Filament would have given the firm a self-service surface for managing users, roles, and lookup tables without me. Cheap leverage I left on the table.
  • Horizon for the queue. The simple queue setup is fine at this scale, but I would not bet on it scaling with the firm. Redis plus Horizon gives me visibility and back-pressure I currently squint at logs to find.
  • Tenant-ready data model on day one. The schema is single-tenant by design. If another firm ever wants the same platform, I would re-derive the membership model with a tenant boundary up front rather than retrofit it.
  • An export feature, properly. The bulk export story still feels like a feature waiting for a real specification.

What I take away

The hardest parts of this build were not the parts I could anticipate from a feature list. They were the access model, the template authoring problem, and the small infrastructure choices that decide whether a platform stays operable by one person. Those problems are worth more on this build than any framework choice was.
